Architecture Evolution

The Short Story: Why This Repo Exists

How table components outgrew monolithic chaos and evolved into pure declarative blueprints.

Front-end web tables are deceptively simple on the surface, but notoriously fragile in production.

In early architectures, every table implementation was a tangled monolith: column iterating loops, header HTML templates, cell calculators, and event click handlers were fused together in one huge JavaScript file.

Whenever a search filter was triggered or new columns were toggled, the entire table element was blown away and rewritten with innerHTML. This introduced severe bugs:

  • Typing in the search input destroyed the input element, instantly stealing user typing focus.
  • Unit testing was impossible without mocking the full browser DOM.
  • Reusing the transformation logic for non-table structures (cards, lists, grids) required duplicating code.

json-renderers-build-table solves this by breaking the monolith into a pure specification pipeline. It takes JSON columns and JSON data, runs declarative instruction recipes without touching the browser DOM, and delegates all events to a persistent container listener.

// The Clean 2-Step Execution:
import { render, hookEvents } from "json-renderers-build-table";

// 1. Pure layout rendering (zero event coupling)
render({
  data: records,
  columns: columnDefs,
  targetHtmlId: "table-container",
  type: "withSearchAndFooter"
});

// 2. Container-level event delegation (never drops search focus)
hookEvents({
  container: "table-container",
  dataset: records,
  columns: columnDefs,
  onSearch: (q, filtered) => console.log("Filtering:", q),
  onSave: (record) => console.log("Save footer:", record)
});
Deep Architectural Comparison

Normal Table Build vs. This Repo Table Build

Comparing the common imperative front-end pattern against our declarative, decoupled AST pipeline.

Normal Table Build (Imperative Monolith)

What most developers write in vanilla JS, jQuery, or ad-hoc custom components:

  • String Interpolation & innerHTML: Stitches HTML strings via template literals (<tr><td>${item.name}</td></tr>). Prone to XSS and broken tags.
  • Search Focus Destruction: Filtering re-renders the whole container. The search <input> is destroyed and re-created on each keystroke, losing cursor position and focus.
  • Interleaved Event Binding: Attaches onclick listeners to individual buttons or row elements. Causes memory leaks when rows are repeatedly added or removed.
  • Heavy DOM Thrashing: 500 rows with 8 columns creates 4,000 DOM mutation calls directly in the browser thread, causing noticeable UI stutter and layout reflows.
// Fragile imperative pattern:
table.innerHTML = records.map(r => `<tr>...</tr>`).join('');
// Kills input focus and leaks event listeners!

This Repo Table Build (Declarative AST)

The decoupled, instruction-driven architecture of json-renderers-build-table:

  • Pure JSON Contract: Only pure data arrays and columns are supplied. Transformations produce a clean AST specification before touching the DOM.
  • Persistent Search Focus: Container-level event delegation intercepts search keystrokes and only repaints the internal <tbody> rows. Search input never loses focus!
  • Zero-DOM Transformation Engine: json-renderers-run-instructions executes 1D and 2D blueprints in memory with zero DOM dependencies. 100% unit-testable in Node.js.
  • Single Batch Hydration: @keshavsoft/json-to-dom mounts the AST into the target element in a single optimized browser pass, eliminating layout thrashing.
// Resilient decoupled pattern:
render({ data, columns, targetHtmlId, type: "withFooter" });
hookEvents({ container, dataset, columns, onSearch });
